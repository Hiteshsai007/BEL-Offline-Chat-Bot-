## 1. Executive Summary

A lean, offline AI **interface** (not a multi-service enterprise application) for looking up technical fault information. A user asks a question in plain language; the system returns an answer grounded strictly in an ingested knowledge base, with a citation, generated by a real local language model — never a hardcoded or templated response.

Runs entirely on one air-gapped workstation, GPU with ≥4GB VRAM, using Ollama as the inference runtime and Qwen2.5:3B as the baseline model. No component requires network access, cloud APIs, or telemetry.

Every user gets the identical interaction path — no personas, no role-differentiated flows.

Current knowledge base (Phase 1): the fault code table from `IRL_Fault_Codes.pdf` (Sl. No., Error Description, Error Remarks, Error Code). Phase 2 expands to full technical manuals (~278 pages) using the same pipeline and a fuller metadata schema.

## 2. Scope

**In scope:** the interactive interface, the RAG retrieval pipeline, real local AI inference, the minimal glue connecting interface to pipeline, basic offline security hygiene, offline knowledge base updates.

**Out of scope:** a full enterprise application layer (formal multi-endpoint REST product, admin dashboard, RBAC, audit logging); persona-differentiated UX; OCR/image processing; model fine-tuning; multi-node deployment.

## 3. Goals and Success Criteria

| Goal | Design Response | Measurable Target |
|---|---|---|
| Fully offline operation | No outbound network calls anywhere in the stack | 0 outbound connections observed |
| Answers come from a real model, not templates | Every grounded response is generated by the local LLM (Ollama) from retrieved context — no hardcoded/canned answer strings anywhere in the code path | 100% of grounded answers traceable to an actual model call, verifiable by response latency (see below) and logs |
| Knowledge base matches source documents exactly | Ingested content is checked against source text at build time; no paraphrased, summarized, or invented entries | 0 discrepancies between knowledge base entries and source document text, spot-checked per release |
| High retrieval accuracy | Section-aware chunking, metadata filtering, confidence thresholding | ≥90% top-5 retrieval hit rate on a labeled eval set |
| Low hallucination rate | Context-bound prompting, output guardrail, explicit not-found path | <5% unsupported-claim rate on the eval set |
| Fast responses | Quantized 3B model on GPU, small index, response cache | P95 latency <2000ms warm; but never <500ms for a genuine LLM call — sub-second responses on a cold query are a signal the model isn't actually being invoked |
| Simple, maintainable design | One interaction layer + one RAG core + one local model | A new engineer understands the full flow within 2 days |
| Easy knowledge base updates | Manual, versioned, atomic offline re-indexing script | Full re-index in <30 minutes |

## 4. System Design (the Interface)

Single interaction path for every user:

```
User types a question
   → question is matched against the knowledge base (exact code match, or semantic retrieval)
   → matched entries (if any) are passed to the local model as context
   → local model composes a grounded answer, citing the matched entry
   → interface displays the answer, or the fixed not-found message
```

No login tiers, no persona-specific UI, no role-based branching. Session-level follow-up (referring to the previous question) is an optional light convenience, not required for Phase 1.

## 5. RAG Pipeline

**Retrieval:**
- Exact error-code patterns in the question (e.g. `0x0003`) bypass semantic search and go straight to a direct lookup.
- Otherwise, the question is embedded and compared against the knowledge base by similarity. Candidates are over-fetched, then filtered/ranked; anything below a calibrated confidence threshold is dropped.
- If nothing clears the threshold, the interface returns the not-found message **without invoking the model at all.**

**Inference:**
- Matched context + question go to the local model with grounding instructions (Section 13).
- Output passes a citation-format check and a guardrail that flags claims not traceable to a retrieved chunk. Failing the guardrail returns a "documentation insufficient" message rather than an unverified answer.

## 6. Language Model

**Baseline: Qwen2.5:3B** via Ollama, Q4_K_M quantization.

- Fits a 4GB VRAM budget with headroom (≈2.0–2.3GB weights, leaving room for KV cache and runtime overhead); 7B–8B models do not reliably fit.
- Competitive instruction-following/structured-output quality at this size, which the grounding-and-citation design depends on.
- Ships as a standard Ollama tag — no manual conversion needed offline.
- ~25–45 tokens/sec on a 4GB-class GPU, supporting the sub-2s response goal.

**Upgrade path:** a Model Registry maps a logical name to a concrete Ollama tag + inference parameters, so upgrading (e.g. to Qwen3:8B) is a config change, not a code change — justified with the evaluation methodology in Section 16, not general reputation.

| Alternative | Why Not Selected |
|---|---|
| Llama 3.2 3B | Comparable size; Qwen2.5:3B preferred for benchmark performance and Ollama tag maintenance |
| Phi-3.5-mini (3.8B) | Larger footprint, no clear grounding-quality advantage here |
| Mistral 7B / Qwen3:8B | Doesn't reliably fit 4GB VRAM without CPU offload |
| Gemma 2 2B | Weaker structured-citation behavior, higher hallucination/formatting risk |

## 7. Embedding Model

**Recommendation:** BAAI `bge-small-en-v1.5` via `sentence-transformers`, CPU-run.

- CPU-viable at production latency (single-digit ms per chunk); doesn't compete with the LLM for the tight 4GB VRAM budget.
- Strong MTEB retrieval performance among sub-100M-parameter models.
- Fully offline-distributable — weights downloaded once at setup, no runtime network dependency.

| Alternative | Why Not Selected |
|---|---|
| OpenAI text-embedding-3 | Requires a cloud API — disqualified by the offline requirement |
| all-MiniLM-L6-v2 | Weaker retrieval accuracy on technical text |
| bge-large-en-v1.5 | ~10x the compute, not justified unless evaluation shows a need |
| e5-small-v2 | Comparable class; BGE preferred on technical-document track record |

## 8. Vector Store

**Recommendation:** FAISS (`IndexHNSWFlat`, or `IndexIVFFlat` past ~200K chunks).

- In-process library — no server, no network port, no auth surface to misconfigure.
- File-based persistence fits a 1–2-times-a-year update cadence better than a continuous-write database.
- Fast enough at this scale (low single-digit ms search); retrieval isn't the bottleneck, generation is.

| Alternative | Why Not Selected |
|---|---|
| Milvus/Weaviate/Qdrant (server mode) | Introduces a network service unjustified at this scale |
| Chroma | Less mature/battle-tested than FAISS here |
| PostgreSQL + pgvector | Full RDBMS server for a workload with no concurrency need |
| Plain NumPy brute-force | Fine at current scale, doesn't scale into the Phase 2 corpus |

## 9. Knowledge Ingestion & Metadata

Offline script, run manually 1–2 times a year: PDF → parse → clean → detect headings/structure → normalize to Markdown → semantic chunk → extract metadata → embed → build/rebuild FAISS index → **validate against source** → atomic swap into production.

**Fidelity requirement (non-negotiable):** every ingested chunk's text must be traceable back to the exact source document content — no summarization, no paraphrasing, no invented detail, at ingestion time or in any cached/example data used during development. This was violated once during prototyping (a placeholder knowledge base with fabricated fault-code meanings was built instead of the real table) and must not recur. Any example/test data used during development must be clearly labeled as such and never substituted for the real source silently.

**Metadata schema** (kept in full for Phase 2 manuals):

```json
{
  "chunk_id": "uuid4",
  "document_name": "string",
  "document_version": "string (e.g. Rev-C, 2025-01)",
  "system_name": "string",
  "subsystem": "string | null",
  "chapter": "string | null",
  "section": "string | null",
  "page_number": "integer",
  "error_code": "string | null",
  "chunk_type": "prose | table | procedure",
  "token_count": "integer",
  "source_hash": "sha256 of source PDF for provenance"
}
```

**Current data availability (Phase 1):** `IRL_Fault_Codes.pdf` provides only serial number, error description, error remarks, and error code. `document_version`, `system_name`, `subsystem`, `chapter`, `section`, and `page_number` are left `null` — not guessed — until confirmed or superseded by Phase 2 manual ingestion.

## 10. Functional Requirements

| ID | Requirement | Description |
|---|---|---|
| FR-1 | Natural Language QA | Accept free-text questions, return an answer grounded in retrieved documentation |
| FR-2 | Semantic Search | Retrieve by embedding similarity, not keyword matching alone |
| FR-3 | Error Code Direct Lookup | Bypass semantic search on an exact/partial error-code pattern |
| FR-4 | Real Model Generation | Every grounded answer is produced by an actual local LLM call, never a hardcoded string |
| FR-5 | Grounded Responses | Never answer using information absent from retrieved chunks; enforced by the guardrail check |
| FR-6 | Source Citations | Every grounded answer includes source + error code/section, to the extent metadata is available |
| FR-7 | Unknown Query Handling | If no entry meets the confidence threshold, explicitly state the information is unavailable |
| FR-8 | Graceful Failure Handling | Any pipeline stage failure degrades to a clear error message, never a silent wrong answer |
| FR-9 | Knowledge Base Update | Performed via an offline script; not exposed through the interactive interface |
| FR-10 (optional) | Session Follow-up | Resolve references to the immediately preceding question, as a light convenience |

## 11. Non-Functional Requirements

| Category | Requirement |
|---|---|
| Performance | P95 latency <2000ms warm, <2500ms cold — but a genuine LLM round-trip should never resolve in single-digit milliseconds; that indicates the model isn't actually being called |
| Reliability | No single component failure corrupts the production FAISS index (atomic swap) |
| Offline Execution | 100% of runtime dependencies pre-installed at setup; zero runtime network fetches |
| Maintainability | Configuration externalized (YAML); each pipeline stage independently testable |
| Scalability | Must support corpus growth to at least the Phase 2 manual set (~278 pages) without redesign |
| GPU Constraints | Total resident GPU memory ≤3.5GB, leaving a 500MB safety margin on a 4GB card |
| Memory Constraints | Host RAM for the interface + RAG core under 4GB steady-state (excluding OS and Ollama) |

## 12. Security Considerations

- No internet access — air-gapped, default-deny outbound at OS level.
- No cloud APIs — every model runs locally; no code path references an external hostname.
- No remote inference — Ollama listens only on `127.0.0.1`.
- No telemetry — offline flags set for Hugging Face/`sentence-transformers` at install time.
- Local-only logs and storage, restricted to the service account via OS permissions.

Anything beyond this (encryption at rest, access tiers, audit trails) is explicitly deferred — see Section 19.

## 13. Prompt Design

Four enforced behaviors, each tied to a hallucination-reduction mechanism:

- **Context-only answering** — answer only from the numbered context chunks, never outside knowledge.
- **No speculative bridging** — don't infer unstated information; reinforced by the output guardrail.
- **Mandatory not-found path** — a fixed, non-paraphrasable fallback sentence.
- **Mandatory citation format** — checked in post-processing; a response missing citations where chunks were used is rejected and regenerated once before falling back to an error state.

```
System: You are a technical assistant restricted to the provided context.
Rules:
- Answer only using the numbered context passages below.
- If the answer is not present in the context, respond exactly with:
  "This information is not available in the current documentation."
- Cite every supported statement as [Document, Error Code/Section].
- Do not use any knowledge beyond the provided context.

Context:
[1] {chunk_1_text} - {chunk_1_metadata}
...

Question: {user_question}
```

## 14. Error Handling

| Condition | System Behavior |
|---|---|
| No relevant entries found | Return the fixed not-available response; log the query locally |
| Confidence below threshold | Treated identically to no-relevant-entries |
| Document fails to parse (ingestion) | Log the failing file, halt that file, continue the batch |
| Embedding generation fails | Query-time: graceful "temporarily unavailable" message. Ingestion-time: halt and report |
| Vector search fails | Fall back to the last known-good index, log an alert locally |
| LLM inference fails | Return a clear "service degraded" message — never substitute a canned answer |
| Knowledge base unavailable | Report this state explicitly rather than returning empty or wrong results |

## 15. Technology Stack

| Layer | Technology | Justification |
|---|---|---|
| Language/Runtime | Python 3.11 | Mature ML/NLP ecosystem |
| Interaction layer | Lightweight local service connecting the interface to the RAG core | Just enough surface for one interface |
| Inference Runtime | Ollama | Simplifies local model management |
| LLM | Qwen2.5:3B (Q4_K_M) via Ollama | See Section 6 |
| Embedding Model | `bge-small-en-v1.5` via `sentence-transformers` | See Section 7 |
| Vector Store | FAISS (`faiss-cpu`) | See Section 8 |
| Metadata/Session Store | SQLite | Zero-config, file-based, matches single-host deployment |
| PDF Parsing (ingestion) | PyMuPDF, `pdfplumber` for tables | Layout-aware extraction, strong table recovery |
| Config Management | YAML + Pydantic Settings | Externalizes tunables without code changes |
| Logging | Python `logging` + local rotation | Local-only, matches Section 12 |

## 16. Evaluation Plan

| Metric | Definition | Method |
|---|---|---|
| Retrieval Accuracy | % of labeled test questions where the correct entry is in top-5 | Curated eval set with ground-truth entry IDs |
| Grounding Accuracy | % of answers where every claim traces to a cited entry | Manual review of a sampled subset per release |
| Hallucination Rate | % of answers with at least one unsupported claim | Complement of grounding accuracy; release-blocking |
| Response Time | Mean and P95 end-to-end latency | Load test against representative queries |
| Index Build Time | Wall-clock time for a full rebuild | Timed per ingestion test run |

## 17. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Small (3B) model underperforms on complex multi-step questions | Guardrail + confidence thresholding limits blast radius; upgrade path in Section 6 |
| GPU VRAM headroom is tight (4GB) | KV cache size capped via config; monitored before any change ships |
| Air-gapped install means dependency issues can't be fixed on-site | Dependencies bundled into a single offline installer with checksum verification |
| Poorly structured/scanned PDFs defeat the non-OCR pipeline | Ingestion validation rejects/flags PDFs with near-zero extractable text |
| Development shortcuts (mock/placeholder data) silently ship as if real | Fidelity requirement in Section 9; any test data must be explicitly labeled and never substituted for production content |
| Corpus growth beyond current scope degrades FAISS or the rebuild assumption | Re-evaluate index type once assumptions change materially |

## 18. Assumptions

- Source PDFs are text-native; no OCR is performed.
- Target hardware (GPU ≥4GB VRAM, modern CPU, adequate SSD) is provisioned before Phase 1 begins.
- Documentation updates occur 1–2 times per year, justifying full-rebuild-over-incremental indexing.
- The knowledge base, once ingested, is treated as ground truth; this document doesn't cover fact-verification of the source documents themselves.
- A single-host deployment is sufficient.
- Every user's interaction is identical — no persona/role differentiation.
- The current fault-code source doesn't specify a document version, system name, subsystem, chapter/section, or page number — those fields stay unpopulated until confirmed.
- English-language documentation and queries only, for now.

## 19. Roadmap

**Phase 1 — Fault Code Interface (current):** interaction layer + RAG core + inference against the fault code table; offline ingestion script; baseline eval set (50+ Q&A pairs).
Acceptance: P95 latency under 2s; ≥90% retrieval accuracy on the Phase 1 eval set; zero outbound network connections during a full test run; every knowledge base entry verified to match the source document verbatim.

**Phase 2 — Full Manual Expansion:** ingest the ~278-page manual corpus; populate the full metadata schema; validate Markdown-intermediate conversion and chunking on real prose/procedural/table content.
Acceptance: full re-index under 30 minutes; ≥90% top-5 retrieval accuracy maintained; hallucination rate under 5%.

**Future (not scoped yet):** cross-encoder reranking, hybrid (BM25 + dense) search, multi-document support, knowledge base versioning, incremental updates if churn increases. Access control/audit logging are explicitly not planned as part of this interface's scope.
